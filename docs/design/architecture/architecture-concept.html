cl_audit: one background agent

A ground-up look at how cl_audit runs, where the current design is inconsistent, and a target design in which every job has exactly one owner. Concept only: nothing is built until you pick.

In short. Today each profile's Dock icon app does everything for its profile: it reads the usage, renews the sign-in, sends alerts, starts at login and opens or quits Claude windows. Because of that, an app has to keep running even for profiles that show nothing, and anything that quits a Dock icon also stops its usage.
  • Target: one background cl_audit agent reads the usage and sends the alerts for every profile. It also runs the opening and closing rules.
  • Dock icons only show the usage and handle clicks. They exist only while Usage in the Dock is on.
  • The cl_audit window is only the dashboard, settings and launcher. Quitting it changes nothing.
  • Result: closing a window or quitting a Dock icon can never stop usage or alerts. A usage only profile installs nothing. There is one login item and one source of notifications.

1How it works today

The app is one program that plays two roles. Opened as cl_audit, it is the window. Copied into /Applications/cl_audit <profile>.app with a profile id inside, it is that profile's Dock icon app. They share two files and talk through system notifications.

2Where it's inconsistent

Reading usage depends on showing it

The app that reads a profile's usage is the same app that draws its Dock icon. To hide the icon, the app must keep running in the background, so "Usage in the Dock off" still means an app, a login item and a process. Turning it on or off restarts the app.

Quitting a Dock icon stops the usage

The dashboard's Dock icon switch, the Dock menu's Quit, and "quit the Dock icon with its window" all stop that profile's usage and alerts too. That's the Work bug you found: closing its Claude window quits its collector.

Some rules need cl_audit open

"Start the Dock icon when the window opens" runs in cl_audit, which isn't always running ("starting needs cl_audit running"). The same setting works or not depending on whether a window happens to be open.

The opening and closing rules live in three places

Each profile app, cl_audit's installer, and the dashboard's own prediction of what will happen next. Each special case (no window, no Dock icon, usage only) has to be handled in all three. The window-only case was missed.

Settings that contradict each other

Open at login and "the Dock icon follows the window" can both be on and disagree. Usage only quietly overrides Open at login. The effective behaviour is worked out in scattered small rules, not in one place.

One of everything per profile

Each profile has its own login item, notification permission, sign-in reader, renewal timer and copy of the whole app. Every release reinstalls and restarts all the copies, including the ones that show nothing.

Two sources of truth for the Dock

The config says whether a profile is in the Dock. Each profile app also changes the config when it notices it was dragged out. About a third of all changes so far went into keeping the Dock and the settings in step.

A stopped reader looks like stale data

When a profile app isn't running, its usage just gets old. The dashboard can't tell "nothing is reading" from "Anthropic didn't answer".

3Design rules

One owner per jobReading, showing and controlling are separate, and each has exactly one owner.
Reading never depends on showingUsage is read and alerts are sent for every profile, whatever is open, quit or hidden.
Switches only add or remove what they nameUsage in the Dock adds or removes a Dock icon. Claude window adds or removes a window. Nothing else.
The config says what you want; one place works out what runsEvery process asks that place, so a special case is handled once.
No new moving partsKeep the same files and system notifications, and the same Keychain reading. No server, no new permissions beyond one login item.

6Required changes

  • New: the agent. A small helper app inside cl_audit.app (same program, a third role), registered as cl_audit's one login item. Built and signed by build.sh.
  • Reading moves to the agent. Fetching, sign-in reading, account check, renewal and alerts move out of IconApp.swift into one scheduler for all profiles, with each profile's own interval and backoff. The status line fallback moves too.
  • Dock icon app slims down. IconApp.swift keeps the tile, clicks, menu and details panel, and reads the saved usage when told it changed. Removed: the network, the Keychain, renewals, alerts, its login item, the hidden mode and its restart, the window rules, and config writes.
  • Opening and closing rules in the agent only. Out of IconApp.swift (window watching, quit with window), Config.swift (starting followers, "waits for window") and the dashboard's guesses in Launcher.swift.
  • One profile model. In Config.swift: Dock icon runs replaces Open at login and the Dock icon half of the lifecycle; window follows the Dock icon keeps the other half. One function answers "what runs for this profile", and every process uses it. Old configs are migrated.
  • Saved usage. Written only by the agent, with an "alive" mark and a "changed" notice. The config is changed only through one locked write.
  • Installer. Installs a Dock icon copy when Usage in the Dock is turned on and removes it when it is turned off; the Dock place is remembered with the profile. No longer starts apps: the agent does.
  • Dock. The agent is the only writer, through the existing one-writer path. The hidden mode and its restart go away.
  • Settings and dashboard. Settings.swift: the new Opening and closing card. NewAccount.swift: "Start reading usage" installs nothing. Launcher.swift: the Dock icon switch is only the icon; the main display shows the agent's state.
  • Clean-up for existing installs. Removal.swift: take out the old per-profile login items and the hidden apps of usage only profiles, once.
  • Words. README (How it works, Security: one reader of the sign-in), the site and the CHANGELOG.

8Decisions for you

Where the agent lives: inside cl_audit.app (recommended)

No extra app in /Applications, and it updates with cl_audit. Two alternatives are weaker. cl_audit itself running at login would mean quitting the window stops the usage, which is the same coupling as today. A separate app in /Applications is one more thing to install and keep matched.

Dragging a Dock icon out by hand: keep "the switch follows the Dock" (recommended)

As today, dragging the icon out turns Usage in the Dock off. Only the agent records it, through the one config write.

Dock icons stay separate apps (no choice here)

macOS gives each running app one Dock icon, so a live per-profile tile needs a per-profile app. The target only makes them as small as possible.

9Risks

  • Login item with ad hoc signing. macOS's background item rules are stricter for unsigned helpers; stage 1 exists to find out before anything moves.
  • One reader for all. If the agent stops, every profile goes stale, not one. That's why it's restarted by macOS and the main display says so.
  • Notification permission moves. Old per-profile entries stay in System Settings › Notifications until you remove them; harmless.
  • The usage endpoint isn't public. Same as today; one reader makes a change easier to handle in one place.
