Can cl_audit export and import all sessions?

Research only, 2026-11-05. Nothing was built, written or quitted. Counts, sizes and dates were measured on this Mac without reading what the sessions say. claude-transplant read at v4.2.1, which is still its main (ad7458c, rechecked 2026-11-05; file by file identical). cl_audit at main d94dc7a. Updated the same day with section 3, claude-transplant compared.

Partly: yes for everything kept on this Mac, no for what lives only on Anthropic's servers.

  • Export: yes. Every profile's Claude Code sessions, its Claude window's Code-tab list and its Cowork sessions are plain files, so cl_audit can pack one profile or all of them into one archive, read-only, while Claude stays open.
  • Import of Claude Code sessions: yes, safely. They're barely tied to an account. They can go into any profile, folder or account, or onto another Mac with the same user name, by only adding files.
  • Import of the Claude window's Code-tab list: yes, the way claude-transplant does it. Each entry is copied unchanged under the signed-in account and organisation (only three error keys dropped and the Remote Control ids cleared), and the target profile's window is closed and reopened after a yes. claude-transplant has run this live (a whole Code-tab list, account to account), so it belongs in stage 3, not "later". Sessions that belong to a scheduled task are left out.
  • Cowork: export only. Its records carry the account's name and address, and they're tied to the Cowork virtual machine.
  • Chats, Projects and cloud sessions: no. They're on claude.ai. Its own Settings ▸ Privacy ▸ Export data mails you a copy.

The strongest reason to build it: Claude Code deletes sessions after 30 days (its default; neither profile changes it). Today Main's oldest session is 29 days old. An export is the only way to keep older ones.

3claude-transplant compared

Mostly aligned. Where they differ, the design now follows claude-transplant: the Code-tab list moves in stage 3, and seven of its rules are added: lock, journal, no-clobber writes, its "already there" test, fork parents first, whole task families or none, and the Remote Control clean-up. Decision 1 changes, and two decisions are new.

Both treat a session as one unit: its transcript, the folder beside it (subagents, tool results) and its Code-tab entry. Both keep ids and paths as they are, never overwrite, show a dry run first, and keep a receipt for undo. They differ in purpose:

  • claude-transplant moves entries between two accounts inside the standard profile's folders, where both accounts share one ~/.claude.
  • cl_audit copies sessions between profiles that each have their own folders, so it has to carry the transcript too, and it can do so through an archive.

How claude-transplant moves a session

Read in transplant.js v4.2.1 (5,561 lines). It has one move strategy, rehome; rehomeOne starts at line 2572.

  1. Check that the source entry, its transcript and the folder beside the transcript haven't changed since the plan (fingerprints). Refuse if a running Claude Code worker owns the session, if the id is already in the target, if a fork's parent isn't there, or if a scheduled-task family is incomplete.
  2. Write the entry into <new account>/<new org>/, under the same file name with the same sessionId and cliSessionId. Only three error keys are dropped (error, errorAt, priorErrorMark; line 43) and the Remote Control ids are cleared. The write goes to a private temp file, then appears through a hard link that can't overwrite anything (writeNew, line 734).
  3. If the transcript's last Remote Control pointer belongs to the old account, append Claude Code's own empty pointer line (line 2347). That's its only write to a transcript.
  4. Move the session's scheduled tasks (routines) with it, in each organisation's scheduled-tasks.json (line 3095 on).
  5. Verify, then park the source entry in quarantine in its own folder. Nothing is deleted. undo restores everything from the receipt.
  6. If a session is open in the window, print a plan of exactly what will close and a one-time approval token. Quit Claude gracefully: AppleScript quit on /Applications/Claude.app (line 515), up to 30 s, never force-killed. Move, then reopen.

No export or import: its commands are accounts, keep-local, sweep, finish, undo, restart, menubar and the move itself (parse, line 5166; anything else stops at "unknown command", line 5466). Fixed paths: layout() at line 575 builds every path from the home folder, as Claude/claude-code-sessions, ~/.claude/projects and ~/.claude.json, and main calls it with no arguments (line 5207). There's no option for another window folder or Claude Code folder, so Work is out of its reach.

4What breaks on import

  • Another account or organisation. Claude Code sessions barely mention the account: 5 of 2,000 sampled lines name an organisation. When a window moved to another account, its sessions carried on there (reported by another session, not re-tested). Nothing on Anthropic's side follows: Remote Control and cloud copies stay with the old account. The Code-tab list is filed under <account>/<org> and shows only the signed-in pair's folder, so an import must write into the target's signed-in pair. Cowork records name the account outright, so they don't move.
  • Project paths. Claude Code files a session under a folder named after the project path (/ and . become -), and lists it only when started in that path. On the same Mac, or another Mac with the same user name, paths match. Gone folders (often a quarter or more of a profile's projects) import fine but stay hidden until the path exists again. A different user name changes every path; that's stage 4.
  • Worktrees. Code-tab entries name their worktree. A missing one is shown in the preview before anything is written.
  • Clashing ids. Session ids are random, so they clash only when the same session is on both sides.
    • The target already holds every message and file: "already here", skipped (claude-transplant's test).
    • Grown on either side: the target's copy stays and the archive's is left out. Never overwrite, never merge. A "keep as a copy" option would mean rewriting the id in every line, so it's not in the first version.
    • An entry whose id has a deleted-session marker in the window would vanish again, so the preview flags it.
  • Claude running. Claude Code keeps appending to a session in use. Export copies complete lines only and marks the session "in use". Importing Claude Code sessions only adds new files, so Claude can stay open. The Claude window rewrites its Code-tab list from memory, so importing that list needs that one window closed. As in claude-transplant, the preview lists exactly what closes, and cl_audit closes it gracefully after a yes and reopens it.
  • Forks and scheduled tasks. A forked session needs its parent, so the parent is imported first or the fork is left out. Sessions started by a scheduled task belong to that task's family. claude-transplant moves whole families and refuses incomplete ones; the first version leaves them out and lists them.
  • Remote Control. If a session's last Remote Control pointer belongs to the old account, the import appends Claude Code's own empty pointer line, as claude-transplant does, so the old pointer can't hide the session. The copies on claude.ai stay in the old account.
  • The 30-day clean-up. Claude Code deletes sessions older than 30 days when it starts. Unless the profile keeps sessions longer (stage 0), it could delete old imported ones right away. Which date it goes by still needs a test.

5Safety

  • Never in an archive:
    • Keychain items;
    • .claude.json (account, user id, per-project MCP settings) and .credentials.json;
    • settings.json;
    • sessions/*.json (hold peer tokens);
    • shell-snapshots/ (your shell's environment, which can hold exported keys) and session-env/;
    • telemetry, caches and plugins;
    • the window's cookies, local storage and config.json;
    • Cowork's virtual machine images.
  • Keys inside sessions. Tool output can contain keys, .env files and tokens a command printed, and rewind history keeps old copies of edited files. Before anything is written, export scans for known key shapes:
    • Anthropic, GitHub, AWS, Google, Slack and Stripe keys;
    • private-key blocks;
    • signed tokens;
    • password= lines.
    The preview shows, per session, the kinds and counts found, never the values. Flagged sessions are left out by default. No redaction in the first version, because rewriting would change the history.
  • Add-only. Import never overwrites or deletes. A receipt lists every file it added, with a checksum, and Undo last import removes exactly those, and only if they're unchanged.
  • Written the way claude-transplant writes:
    • one operation at a time, under a lock;
    • every file goes to a temp file first and appears through a hard link that can't overwrite;
    • a journal after every step, so a crash leaves nothing half-done.
  • Export is read-only. It writes only the archive, wherever you save it. The save panel says the archive holds your conversations.

6Recommended design

Sessions belong to a profile, so the controls go on the profile's page in a Sessions card, in layout A: one title with ⓘ, labels of one width each with ⓘ, switches with words, pop-ups, one grey line per row at most. Export and Import each open a page like New profile: settings in cards, then a preview of exactly what will happen. Nothing is written until the last key.

The archive

A single file, cl_audit sessions 2026-11-05.zip, made with macOS's own ditto, so Finder opens it. With a password it becomes an encrypted disk image instead; both are built into macOS. The account is recorded only as a fingerprint of its id, never its address or a token.

manifest.json            format 1 · made by cl_audit <version> · this Mac's home path
                         per profile: name, folders, account fingerprint
                         per session: id, kind, project path, title, first and last activity,
                                      files with size and checksum, keys found (kinds and counts), in use
profiles/<profile>/claude-code/projects/<project>/<id>.jsonl  (+ <id>/subagents, tool-results, workflows)
profiles/<profile>/claude-code/file-history/<id>/
profiles/<profile>/claude-code/plans/                          (if chosen)

profiles/<profile>/cowork/local_<id>/                           (if chosen; conversation, log, uploads, outputs)

Dry run is built in: both previews read everything and write nothing. Import compares checksums with the target first, so "already here", "grown in both places" and "deleted marker" are known before the key is pressed.

8What you'd decide

  1. How far the first version goes (changed after the claude-transplant comparison): stages 0–3 with the Code-tab list in stage 3, about 6–8 days (recommended), or Claude Code sessions only, about 5–6 days?
  2. Keep for: may cl_audit change how long Claude Code keeps a profile's sessions (it writes one setting into that profile's settings.json)? If yes, what default: Claude Code's 30 days, 90 days, a year, always?
  3. Sessions with keys found: left out by default (recommended), or kept but only with a password?
  4. Archive: zip, plus an encrypted disk image when a password is set (recommended), or always encrypted?
  5. Cowork in exports: off by default (recommended; few sessions use it), or on?
  6. Another Mac with a different user name (stage 4): needed now, later or never?
  7. New: copy only, or also Move? Between two profiles on this Mac, Move would park the source session in quarantine after the import checks out, as claude-transplant does, so only one live copy remains and Undo brings it back. Recommended: copy only in the first version, Move later.
  8. New: scheduled tasks. Leave sessions started by a scheduled task out and list them (recommended for the first version), or move whole task families as claude-transplant does (later, +1–2 days)?
