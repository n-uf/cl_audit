Moving a profile's whole Code sidebar

Research only, 2026-11-05. Nothing written, quit or signed in. Measured by counting entries and reading key names and lengths in the two Claude windows' folders, and by the app's own read-only sidebar listing. No titles, group names or contents were copied out. claude-transplant v4.2.1 (its main). Findings only; the UI sketches are the hub's (cl-audit-session-move-sketch.html). Export/import stays as the second feature (section 8); its page is unchanged.

Correction, 2026-11-05 (later the same day): the sidebar is synced to claude.ai. A closer read of the Claude app's code shows the sidebar store syncs per account and organisation to /api/claude_code/organizations/<org>/user_settings, and the server's copy is merged in when an account signs in. Synced: groups, which session sits in which, order, sections, pins, sort and group-by. The Local Storage store and the claude_desktop_config.json mirror on this Mac are caches of it. The statements below that it's local only are wrong.
  • For the move: sessions and scheduled tasks are local files and move as described. The sidebar should be rebuilt through the app once the window is signed in as the new account: a new Claude Code session, opened by cl_audit with its prompt filled in (claude://code/new?folder=…&q=…), applies the plan with the app's own sidebar tools, and the app syncs it.
  • Then: each account keeps its own synced sidebar, and session ids don't change, so later switches only file the sessions made since.
  • Signing out of the window is harmless for the sidebar: the server's copy comes back at sign-in.

The whole sidebar can move. It's two jobs, though. (See the correction above: the sidebar is also kept on claude.ai.)

  • The sessions themselves: entries, titles, archived and starred state, and scheduled tasks. They move the way claude-transplant moves them, which has been run live.
  • The sidebar's structure: sections, custom groups and their order, which session sits in which group, pins and collapsed state. It sits in the window's own settings stores, in a private format kept in two copies: a live browser-storage copy and a mirror in claude_desktop_config.json. No tool writes it today, claude-transplant included. That's why groups have had to be rebuilt by hand after an account switch. A short test has to show which copy the app trusts at start before cl_audit writes it. The safe fallback is to let the app write it through its own sidebar tools.
  • Store is the same move with cl_audit's own folder as the destination, plus the transcripts, so Claude Code's 30-day clean-up can't take them.
At a glance, for the sketch's "depends on research" parts. Everything is in the Claude window's own data folder, filed under <account>/<org> except where it says otherwise.
  • Sections (built-in and custom, with order, shown, collapsed, sort and grouping): codeSidebarByScope in Local Storage's dframe-store, mirrored as dframe-code-sections in claude_desktop_config.json.
  • Groups, which session sits in which, and the order inside a group: customGroupsByScope (groups, assignments, order), mirrored as dframe-group-scopes.
  • Pins (pinnedOrder, navPinnedIds) and collapsed groups: Local Storage only, for the whole window, by session or group id.
  • Titles, archived, starred, who started a session: inside each session's entry, claude-code-sessions/<account>/<org>/local_<id>.json.
  • Scheduled tasks: scheduled-tasks.json beside the entries.
The sidebar parts are also synced to claude.ai per account and organisation (see the correction at the top).

1Where the sidebar lives

Each Claude window has its own data folder: the standard one for Main, Claude-work for Work. Inside it, everything about the Code sidebar is filed under a key made of account id / organisation id. The window shows only the key it's signed in to.

The sessions

claude-code-sessions/<account>/<org>/
  • local_<id>.json: one entry per session, holding title, archived and starred state, worktree, the session that started it, and the account's connector list (names and addresses, no tokens) PER ACCOUNT
  • scheduled-tasks.json: the routines PER ACCOUNT
  • archived-sessions.idx: a list of archived ids the app keeps up itself PER ACCOUNT
  • deleted_<id> markers PER ACCOUNT

The structure, live

Local Storage › dframe-store (claude.ai origin)
  • codeSidebarByScope: the sections (built-in Pinned, Routines, Sessions and custom ones) with order, shown, collapsed, sort and grouping PER ACCOUNT
  • customGroupsByScope: groups (id, name), which session is in which group, and the order inside each group PER ACCOUNT
  • pinnedOrder, navPinnedIds, collapsedGroups, sort and group-by choices, folder colours, sidebar width WHOLE WINDOW
  • plus "persisted" copies of the sections, groups and starred lists LIVE

The structure, mirror

claude_desktop_config.json › preferences.epitaxyPrefs
  • dframe-code-sections and dframe-group-scopes: the same sections, groups, assignments and order, key for key PER ACCOUNT
  • code-projects-order, starred-* lists
  • The file also holds MCP server settings, which can contain secrets. cl_audit may only ever change the sidebar keys.
Synced to claude.ai (corrected). Groups point at local session ids (code:local_…), but the store itself syncs per account and organisation to claude.ai (/api/claude_code/organizations/<org>/user_settings). The ccd-sync-pending:ccd/dframe-store key marks an upload still waiting. An earlier account's structure is still here because each account keeps its own synced copy.
Group membership is partly inherited. In the sidebar measured, most sessions shown in a group weren't filed there directly (about one in six was). A session started from another session shows in its starter's group: in one group, nearly every session was there only that way. Entries keep who started them, so membership follows when the entries move together.

2What claude-transplant moves, and what happens to the groups

It moves the entries and their scheduled-task families only. transplant.js never mentions claude_desktop_config, epitaxy, dframe or Local Storage. Title, archived and starred state travel because they're inside the entry (its DURABLE_RECORD_KEYS, line 45). After a move:

  • In the new account: the sessions show under the default Sessions section, grouped by project. Sessions inherit their starter's group only if that group exists here, and it doesn't, because groups are per account.
  • In the old account: its groups and assignments stay, pointing at sessions that are no longer there. The Mac measured shows exactly that: dozens of dangling assignments.
  • Pins: they're kept for the whole window by session id, and ids don't change, so pins probably survive. There were none to check on the Mac measured.

3Switching a window to another account, and back

  • Switch: the window shows the new account's folder and the new account's sidebar. A first-time account gets the three built-in sections and nothing else. Nothing of the old account is changed or deleted.
  • Switch back: the old account's sessions and structure show again as they were. That follows from how the data is laid out; it wasn't tried, since switching was out of bounds.
  • Switch back after a claude-transplant move: the old groups come back empty, because their sessions are gone, and the new account's groups stay where they are.
  • cl_audit can see a switch without asking: the window's config.json records the last account, and a new account scope appears in the stores.

4Writing it safely, and how ids map

  • Only with that window closed. The live copy belongs to the running window and is rewritten from memory. cl_audit closes only that profile's window, which it can tell apart by its data folder, after a yes, gracefully, and reopens it afterwards.
  • Two copies. If cl_audit writes, it writes both the mirror (plain JSON, sidebar keys only) and the live copy, or proves first that the app rebuilds one from the other at start. The live copy is a Chromium database, the riskiest file in the plan. Hence a test first, and a fallback: let the app write it. The Claude window has its own sidebar tools (create group, move sessions, pin, sections), used today from inside a session. cl_audit can leave a sidebar plan for a session in the target window to apply, so every write goes through the app.
  • Id mapping when the target already has sessions and groups:
    • Sessions keep their ids (claude-transplant's rule). The same id in the target means "already there", or a refusal. Never overwrite.
    • Groups match by name. A group with the same name is reused, keeping the target's id; otherwise a new group goes after the target's own, in the source order.
    • Assignments are rewritten to the target's group ids. Only the direct ones need writing; inherited membership follows the entries.
    • Order inside a group: the moved sessions go after the target's, in their source order.
    • Built-in sections: the target keeps its own settings, unless it's a first-time account still on defaults; then it takes the source's.
    • Pins: moved pinned sessions are added after the target's pins.
    • Scheduled tasks: move as whole families, or not at all.
  • The source keeps its structure untouched, and its entries are parked in quarantine, not deleted. Undo puts back the entries, and the target's structure from a copy taken just before.

5Store

A Store is a move whose target is cl_audit's own folder, ~/Library/Application Support/usage-n-uf/stores/<date> <profile>/:

manifest.json      when, from which profile, account fingerprint (never the address or a token), counts, checksums
entries/           local_<id>.json exactly as they were
tasks/             the scheduled-task families
sidebar.json       cl_audit's own plain description: sections, groups by name and order,
                   who sits where and in what order, pins, collapsed (no app-private ids except the sessions')
claude-code/       each session's transcript, its subagents and tool results, rewind history

Restore is the same move in reverse, onto the same account, another account of that window, or another profile. It shows a preview first and keeps a receipt. Transcripts go back only where they're missing, and nothing is ever overwritten.

6How a move runs

The UI sketches are the hub's, in cl-audit-session-move-sketch.html. These are the steps and rules they rest on.

  1. Plan, read-only. List what goes and what stays, with reasons:
    • sessions;
    • groups, with which ones join a same-named group in the target;
    • pins;
    • whole scheduled-task families;
    • transcripts to copy when the target uses another Claude Code folder;
    • blocked: running in the window, open in Terminal, already there, id clash, missing fork parent, incomplete task family.
    If claude-transplant has an unfinished move on this Mac (its own folder, ~/Library/Application Support/claude-transplant), refuse until it's finished or undone, so the two tools never work on the same window at once.
  2. Close only the windows involved: the source's, and the target's when it's another profile. Show the exact list first, quit gracefully after a yes, never force-kill.
  3. Move the sessions: entries and scheduled tasks, and transcripts when needed. Originals are parked in quarantine.
  4. Rebuild the sidebar in the target's scope: groups by name, places, order, sections, pins. The method is the one stage 0 picks.
  5. Reopen and check: counts match, and the receipt is saved, with Undo ready.

"Bring here…" is the claude-transplant case. After a window switches accounts, it brings the earlier account's sessions and their groups to the new one. It would also restore the groups and places an earlier account switch left behind.

Rules carried over from claude-transplant

  • Plan first, then an exact list of what closes. Only that profile's window closes, gracefully, never force-killed.
  • Lock, journal after every step, and writes that can't overwrite (temp file, then a hard link).
  • Same ids. "Already there" only if the target holds every message.
  • Sessions running in the window wait for the approved restart. A session Terminal is running is refused until it stops, because restarting the window doesn't stop it.
  • Fork parents first; whole scheduled-task families or none.
  • Drop the old account's error keys; clear Remote Control ids; append the empty pointer line.
  • Originals parked in quarantine; a receipt; Undo.
Added for the sidebar:
  • a copy of the target's structure before the change;
  • only the sidebar keys of claude_desktop_config.json are touched, never its MCP settings;
  • deleted-session markers are checked.

Left out on purpose: claude.ai Remote Control copies. They stay in the old account, with no Keychain cookie read.

8Two features, one engine

The operator keeps both:

  • (a) Move: the sessions setup with its sidebar, to another account, another profile or the store. It stays on this Mac, and the source is parked.
  • (b) Export and import: for backups and another Mac, as designed on the export page. It makes a copy, in an archive file.

9Wrapper on claude-transplant?

It makes sense only for part of the job, and a wrapper can't meet the brief.

  • claude-transplant moves no sections, groups or pins, and reaches only the standard window, so the brief's main ask (the sidebar, for every profile) would still need cl_audit's own code.
  • Recommended: (iii) cl_audit's own move, built on claude-transplant's rules.
    • It never runs claude-transplant, and it waits for any unfinished claude-transplant move.
    • Offering (ii) upstream is a courtesy, not a dependency.

11What you'd decide

  1. The test window (stage 0): may cl_audit's builder make a throwaway Claude window with its own folder, and will you sign it in to two accounts for an hour?
  2. How the structure is written, once stage 0 has answered: directly into the window's stores with the window closed (recommended, if the test shows it holds), or always through the app's own sidebar tools from a session in that window (safest; you'd paste one line into a session there)?
  3. Store: takes the sessions off the account, so the sidebar empties until Restore (recommended, the move you asked for), or keeps a snapshot and leaves the sidebar as it is?
  4. Groups with the same name in the target: joined (recommended), or kept apart as "name (moved)"?
  5. The old account's leftover structure after a move: left as it is (recommended, so Undo is simple), or cleared once the move is checked?
  6. Where the offer appears when a window switches accounts: as the "Earlier account ▸ Bring here…" row in the Sessions card (recommended), or also as a question at the end of the Account change in the Claude Code card?
