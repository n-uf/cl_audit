cl_audit: how profiles and accounts work, and a library for them

An audit of cl_audit at 26.11.24, plus the account fix now being built, B8 (the Claude app and Claude Code on different accounts). Read-only: nothing was changed.

Short answer. You were right. One background agent does read and resolve the accounts. But each screen then makes its own decisions about whose numbers they are, whether they're fresh or full, what colour to use and what button to show. The audit counted about 45 separate decision points and found 14 real inconsistencies. Today's fix shows the cost: one simple rule had to be written into 10 or more places, and the review still found 4 places it missed. The cure is a small library, ProfileCore. It holds all those rules once and hands each screen a ready-made "what to show" value. Screens only draw that value, and the compiler stops them from deciding anything themselves.

Rough shape of the library's interface

public struct ProfileDisplay {
  var account: AccountLine      // label, lamp, note
  var numbers: Numbers          // .shown([...]) | .none(why)
  var codeNumbers: [LimitDisplay]? // the split's labelled line
  var freshness: Freshness      // .fresh | .lastKnown | .stale
  var full: FullLimit?
  var key: PrimaryKey?          // .logIn | .logInClaudeCode(to:)
  var standby: [StandbyLine]
  var offer: StandbyLine?
}
public enum Display {
  static func make(profile:, record:, all:, now:) -> ProfileDisplay
}

What stays in the app

  • All SwiftUI and AppKit views, colours, the Dock tile and menus
  • The wording, with privacy masking applied when drawn
  • Timers, notifications, the claude command line, Terminal
  • Quick chat's engine. It hands its live numbers into the library and no longer merges them itself
  • The switch, move, import and restore engines (only the switch-receipt model moves)

5 · How it's done in Swift

Today build.sh compiles all 42,000 lines with one swiftc call into one program. Swift has no internal walls until code is split into modules. A module compiles separately, and everything outside it sees only what it marks public.

Recommended · keep swiftc, add a Core/ folder built first
  • One extra compile step builds Core/*.swift into a small library, libProfileCore.a plus its interface.
  • The app, the widget and every check program then import ProfileCore.
  • About 10 more lines in build.sh. release.sh doesn't change.
  • The widget gets the same rules for free, and its hand copies go.
  • A new check suite compiles only the library, proving it needs no UI.
  • Crossing the boundary is a compile error, not a code review.
Alternative · a Swift package (Package.swift)
  • The standard tool, with caching and swift test.
  • But the app bundle, the launcher and code signing stay in build.sh anyway. That means two build systems.
  • The widget extension needs unsafe flags under a package.
  • The check suites are custom programs, not XCTest. Whether XCTest even runs with only the Command Line Tools is unsure.
  • Still possible later: Core/ would already be a clean package target.
swiftc -parse-as-library -module-name ProfileCore -application-extension \
  -emit-module -emit-module-path build/ProfileCore.swiftmodule \
  -emit-library -static -o build/libProfileCore.a Core/*.swift
swiftc … -I build -L build -lProfileCore Sources/*.swift    # the app, the widget and checks do the same

7 · Risks to watch

  • Keychain. Keep reading through /usr/bin/security, which never prompts. The token never enters a file, log or saved type, and only the agent reads it, never the Dock icons or the widget.
  • Several running copies. Dock icons are copies of the app, so an old icon can read a new status file during an update. File changes must only add fields.
  • The widget. It's sandboxed and an app extension, so the library may not use AppKit app-only APIs. Compiling with -application-extension enforces that.
  • Saved files. accounts.json must round-trip every key, including legacy ones, and keep the pre-version backup. status/*.json keeps its old fields for at least one release.
  • Checks. The sign-in and backup suites are missing from the repo, so step 1 restores those checks first. The text-based screen check moves along with the code.

Start with steps 0 and 1: land today's fix, then build the library and its build step with the simple rules. Each later step is its own small release. Or keep this as a plan for now.
