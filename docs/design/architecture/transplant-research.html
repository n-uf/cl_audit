claude-transplant and cl_audit

Research only: nothing was installed, run, committed or changed, and no Claude profile, folder or Keychain item was touched. 2026-11-03, updated the same day with the Claude Space session's account switch and its answer on which login moved. claude-transplant read at v4.2.1 (2026-11-01); cl_audit read at commit 12f3012 (widget redraw on install).

Short answer

  • Your account switch is exactly the case claude-transplant handles. The Claude Space session moved the standard Claude window to a fresh Ultra account, and claude-transplant carried about 100 Code sessions over. It worked, and its undo is still available on this Mac.
  • In cl_audit, that's the standard profile only. The tool's paths are fixed to ~/Library/Application Support/Claude and ~/.claude/projects. Every other profile keeps its sessions in its own folders, out of the tool's reach.
  • Right now cl_audit is watching the old account. Claude Space confirmed that only the desktop app signed in to the new account. Claude Code's login in ~/.claude, which cl_audit reads usage from, is still the old account. So:
    • the standard profile's numbers in cl_audit are the old account's;
    • Claude Code in Terminal still runs on the old account;
    • cl_audit doesn't track the new Ultra account at all.
    The fix is in open question 1.
  • cl_audit doesn't notice a switch. Once a profile is linked to an account seat, cl_audit never updates that link. When ~/.claude moves to the new account, the standard profile will show the new account's usage but stay linked to the old seat. cl_audit would then refuse the old account as a new profile, and wouldn't treat the new account as taken. This comes from reading the code; it wasn't tested.
  • Not safe with other Claude windows open. When the tool restarts Claude, it takes the first Claude process it finds, then quits and reopens the app as a whole. With other profiles' windows open, it can hit the wrong one.
  • Recommendation, in order:
    1. Write the switch down as a short how-to in cl_audit's README.
    2. Make cl_audit notice when a profile's account changes and offer to relink it. That's needed whether or not you use claude-transplant.
    3. If you'll switch accounts again, add a guided "Change account…" in cl_audit. It would do the backup, quitting, sign-in, relink and usage check, and hand the session move to claude-transplant for the standard profile.
    Don't bundle the tool inside cl_audit.

What the Claude Space session did

The Claude Space session reported this; it wasn't re-checked here. The goal was to sign the Claude desktop app in to a fresh Ultra account, so the weekly limit starts from zero, without losing the Code sidebar. The session left out a separate workspace clean-up (sidebar sections, a folder rename, rewriting sessions' working folders), and the same should go for any cl_audit feature.

  1. Back up (Claude can stay open). ~/.claude went into ~/claude-config-backup-<date>.tgz. ~/Library/Application Support/Claude/, minus caches, was copied to ~/Claude-profile-backup-<date>/.
  2. Optional: check that the new account signs in, without touching the old one: CLAUDE_CONFIG_DIR=~/.claude-newacct claude, then /login.
  3. Quit the Claude desktop app.
  4. Run npx claude-transplant (npx runs an npm package without installing it; needs Node 22). Pick the old account and organisation as From and the new one as To. The tool lists the open sessions it would affect and the restart it needs, then prints a one-time approval command. In v4.2.1's code that's --restart-approved <64-hex token>; Claude Space calls it --approve <hash>.
  5. Run the printed command. It quits and reopens Claude gracefully, moves the records from the old account's folder to the new one's, checks them ("chat messages unchanged ✓"), puts the originals in quarantine under ~/Library/Application Support/claude-transplant/ and writes a receipt.
  6. Sign in to the new account in the desktop app. The sessions are in the sidebar.
Checked afterwardsSessions present, the right plan, the weekly limit reset (about 90% on the old account, 0% on the new).
Not switchedClaude Code's own login in ~/.claude: oauthAccount in ~/.claude.json still names the old account (Claude Space checked it). Nobody ran claude auth login for the new account. The claude setup-token run earlier was for the old account's CI token. So the reset applies to the desktop app's sign-in only.
Doesn't follow the switch

  • claude.ai connectors and MCP servers (tools Claude can call): reconnect them.

What claude-transplant does

vitaliyhayda/claude-transplant: a command-line tool, plus an optional menu bar app, for macOS.

  • The problem: the Claude desktop app keeps one small record file per Code session, claude-code-sessions/<account>/<organisation>/local_<id>.json in its data folder. It lists only the folder of the account you're signed in to. The conversations themselves (transcripts) sit in ~/.claude/projects, where every account can read them.
  • What it moves: only those record files, from one account's folder to another's inside the same data folder, keeping each session's id. Transcripts stay where they are. Each move writes the new record, checks it, puts the old one in quarantine (not deleted) and saves a receipt for undo.
  • Covers: the desktop app's Code tab only. Claude Code in Terminal doesn't have this problem, because claude --resume reads the transcripts whoever is signed in. It doesn't touch claude.ai chats or Projects, or the VS Code extension.
  • Sessions in use: the desktop app rewrites the records it has open from memory. A session whose Code worker (the Claude Code process behind it) is running waits for an approved, graceful restart; nothing is force-killed. Sessions run by Claude Code in Terminal are always refused.

How cl_audit is built, for this question

  • A profile is one seat (one account in one organisation), and no two profiles share one.
    • Each profile has its own Claude Code folder.
    • Every profile except the one using ~/.claude also has its own desktop data folder (~/Library/Application Support/Claude-<id>). The profile using ~/.claude uses the standard Claude window.
  • How a profile gets its seat: FolderRules.linkSeats links a profile to the seat its folder is signed in to, once, and from then on leaves linked profiles alone. The "Wrong account" warning compares two things: the email the agent sees for the login, and the email in the folder's .claude.json. After a clean switch, both say the new account, so nothing warns that the saved seat is still the old one.
  • Keychain naming: Account.keychainServices gives Claude Code-credentials for ~/.claude. For any other folder it's Claude Code-credentials-<sha8>, tried for the path with and without a trailing slash.
  • Three roles, one program:
    • The agent reads usage and the plan for every profile. It is the only part that reads the Keychain, and it starts and quits Dock icons and Claude windows.
    • The Dock icons only show what the agent saved.
    • The cl_audit window is the only settings editor: one locked write to accounts.json.
  • Already there, and useful for a switch:
    • sign-in in Terminal for a folder (ClaudeCLI.openLogin);
    • the agent's window quit and reopen, including "Claude is asking";
    • ClaudeRuns.scan, which lists every running Claude window and Claude Code session;
    • the usage and plan reading that would confirm the reset.
  • Never done today: writing into Claude's own data (session records, transcripts), and reading the desktop app's cookie key. The README's security section says so explicitly.

Bundle claude-transplant inside cl_audit not recommended

Shipping its JavaScript in the app means shipping Node 22 or requiring it. It also means following its weekly releases and taking on its bugs (see issue 33), with the menu bar's --cloud path breaking the README's promise about what cl_audit reads.

Risks

Credentials

  • --cloud reads Claude Safe Storage, which unlocks the desktop app's claude.ai sign-in cookie. If that key is shared, as it very likely is, the same read unlocks every cl_audit profile's web sign-in. That's a full claude.ai session, much more than the short-lived usage token cl_audit keeps in memory.
  • Without --cloud, the tool reads no Keychain item. So any cl_audit flow should leave it off.
  • The backups contain every transcript and the desktop app's data, with its cookies still encrypted. Keep them in your home folder only, and delete them once you're sure.

Sessions and windows in use

  • A record moved under a running window gets rolled back, because the desktop app rewrites the records it has open from memory.
  • claude-transplant's appProcess takes the first process running /Applications/Claude.app/Contents/MacOS/Claude, whatever its data folder. Its AppleScript quit and open -a address the app, not one window.
  • With cl_audit's other windows open, three things can happen: the wrong profile's window quits; "reopen" just brings an existing profile window forward; or the move stops with "Open Claude sessions changed". So quit them all first.
  • Its signed-in-account check reads ~/Library/Logs/Claude/main.log, which every window probably writes to (not checked).

cl_audit after a switch

  • Two sign-ins per profile: the standard profile has Claude Code's sign-in in ~/.claude, which is what cl_audit reads usage from, and the desktop app's own. A switch has to move both.
    • This time only the desktop app moved, so the standard window and its profile are now on different accounts. cl_audit's one-seat-per-profile model doesn't expect that.
    • Nothing in cl_audit flags it: its "Wrong account" check compares two records of the Claude Code login, which still agree with each other.
  • Stale seat: the profile stays linked to the old account, as described above. Until option 2 exists, the way out is removing the profile and adding it again. That reinstalls its Dock icon but keeps its folders.
  • Mixed history: the dashboard's usage history reads the profile's Claude Code folder, so it probably shows the old and new account's use as one profile from now on.
  • Sessions landing where no window looks: the tool lists every ~/.claude* folder's account as a target, cl_audit's profiles included. Moving the standard window's sessions "to Work" files them under Work's seat in the standard data folder, which no window shows, because Work's seat belongs to another profile.

Rollback

  • undo reverses only the last move, and refuses if a moved session changed since.
  • ~/Library/Application Support/claude-transplant/ on this Mac is the rollback for Claude Space's move; deleting it makes the move final.

Licence

  • MIT works with cl_audit's PolyForm Perimeter licence. cl_audit may bundle, port or adapt the code, as long as the MIT copyright and permission notice stay with any copied part.
  • Learning the file format and writing new Swift code needs no notice; crediting the project is still good form.
  • Don't use "claude-transplant" as a feature name.

Upkeep, supply chain, data

  • One maintainer, weekly releases, and Claude's private file layout underneath. Pin a version (npx claude-transplant@4.2.1): without one, npx fetches the newest release.
  • Moving personal history into a Team or Enterprise organisation makes it that organisation's data.
  • Since cl_audit is public, check how Anthropic's terms treat moving to a fresh account to reset a weekly limit before cl_audit presents a feature that way.

Open questions for you

  1. Move ~/.claude to the new account too? It's still on the old one.
    • cl_audit shows no Log in… button here, because it sees no mismatch. Do it in Terminal instead: claude auth login with CLAUDE_CONFIG_DIR unset, then sign in to the new account.
    • Afterwards, relink the profile. Until option 2 exists, that means removing the profile in cl_audit and adding it again; its folders are kept, and its Dock icon is reinstalled.
    • If you'd rather keep watching the old account, a better fit is giving the old account its own profile (new folder and window). The standard profile would then follow the new account.
  2. One-off or recurring? If you'll switch the standard profile's account again, option 3 earns its keep. If not, options 1 and 2 are enough.
  3. What happens to the old account? If it comes back as its own profile, it gets new folders and window, and its earlier sessions stay with the new account in the standard window.
  4. Carry sessions between profiles at all? For example, Work's limit is full and you go on in Main. Only option 5 leads there.
  5. May cl_audit write into Claude's own data folders? Only option 5 needs this, and the README's security section would change.
  6. Contribute option 4 upstream? It's a pull request to someone else's repo, so it waits for your go.
